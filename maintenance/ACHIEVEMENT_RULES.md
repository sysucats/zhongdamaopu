# 成就规则通用化设计

目标：把成就系统做成通用的规则引擎。在不影响现有累计阶梯徽章的前提下，支持时间限定（节气、节日、纪念日、限定日期）、按天数或猫数聚合、按条件筛选等各类成就，让以后新增成就类型只需加配置或加一个统计项，不再改动整条链路。下文以节气系列为例说明，它只是其中一种用法。

## 现状与问题

- 规则只有 `{ metric, count }`，`metric` 限 view / follow / photo / comment / like 五种累计计数。
- 计数逻辑写死在 `achievement.js` 的 `countMetrics`，新增统计项要改两处，且无法传入时间范围等条件。
- 只在用户调用 `sync`（打开成就页、浏览猫）时统计并发放。
- 前端 `buildLadders` 把同一系列同一统计项的徽章按门槛排成阶梯，进度显示累计总数，不适合按日期解锁的徽章。

## 设计

整体由五部分组成：**规则（含时间窗口）+ 统计项注册表 + 事件触发发放 + 兜底同步 + 系列展示方式**。

### 1. 规则结构

```js
rule: {
  metric: 'photo',            // 统计项，取自注册表
  count: 1,                   // 门槛
  window: { start, end },     // 可选，北京时间日期 'YYYY-MM-DD'，含首尾两天，只统计窗口内产生的记录
  agg: 'total',               // 可选，total 次数 / days 不同天数 / cats 不同猫数
  filter: { catId },          // 可选，限定条件
}
```

- 现有徽章不带可选字段，行为不变，无需迁移。
- 窗口宽窄由配置决定，代码不区分：
  - 节气：节气日前后各放宽 1～2 天，共 3～5 天。
  - 限定日期：当天 0:00 至 24:00。
- 后台编辑器用开始、结束两个日期选择器填写；开始晚于结束时自动联动另一端。
- **时区**：窗口一律按北京时间（UTC+8）解释。云函数默认按 UTC 运行，换算错会导致单日徽章在 0～8 点错天。
- 上线或已有人获得后，整条规则（含窗口、聚合方式、筛选条件）都不能再改。`sameRule` 需改为整体比较。

### 2. 统计项注册表

每个统计项自带计数函数，并声明支持哪些条件：

```js
const METRICS = {
  photo: {
    label: '上传照片', name: '留影', unit: '张', desc: '上传 {} 张审核通过的照片',
    supports: ['window', 'days', 'cats'],
    count: (db, openid, rule, user) => /* 按 rule 查 photo */,
  },
  view: {
    label: '浏览猫猫', name: '猫口普查', unit: '只', desc: '看过 {} 只不同的猫猫',
    supports: [],             // 无时间记录，不支持窗口
    count: (db, openid, rule, user) => uniqueCount(user?.viewedCats),
  },
  // ...
};
```

- 发放逻辑统一调用 `METRICS[rule.metric].count(...)`，不关心具体统计项。
- 后台校验和编辑器都读取 `supports`，配不出做不到的规则（例如「立春当天浏览」）。
- 同一次检查中条件相同的查询只执行一次（例如五级照片阶梯共用一次计数）。

各统计项的时间依据：

| 统计项 | 集合 | 窗口依据 | 支持窗口 |
|---|---|---|---|
| photo | `photo`（`verified: true`） | `create_date`（上传时间） | 是 |
| comment | `comment`（曾通过审核） | `create_date` | 是 |
| like | `inter`（`type: 10000`） | `create_date` | 是 |
| view | `user.viewedCats` | 无时间记录 | 否 |
| follow | `user.followCats` | 无时间记录 | 否 |

浏览和关注若以后需要时间窗口，再引入通用事件集合 `user_event: { openid, type, target, at }`，本期不做。

### 3. 事件触发发放

在互动写入成功后，只检查与该统计项相关、且当前处于有效期的徽章：

| 统计项 | 触发点 |
|---|---|
| photo | `managePhoto.js` 中 `opType == "check"` 审核通过后 |
| comment | `curdOp.js` 便利贴通过审核时（`approvedOnce` 置为 true 的分支） |
| like | `curdOp.js` 点赞写入 `inter` 后 |
| view | `achievement.js` 的 `recordView` |
| follow | `updateFollowCats.js` |

- **触发时间与判断依据分离**：在审核通过时触发，但按记录的上传时间判断是否落在窗口内。立春上传、三天后才审核通过的照片照常发放，无需额外宽限期。
- 窗口判定：只检查 `start ≤ 上传时间 < end` 的徽章。触发时窗口已结束不影响判断，因为依据的是记录本身的时间。
- 发放失败只记日志，不影响主操作（审核、点赞等照常成功），由兜底同步补发。
- 发放沿用现有的 `serials.allocate` 和确定性 `_id`，并发安全不变。

### 4. 兜底同步

保留现有 `sync`，作为补发路径，覆盖两种情况：

- 新上线累计徽章时，已达标的老用户要等下一次相关操作才会触发。
- 事件触发发放失败。

调用时机：打开成就页时调用一次，不必在浏览猫时频繁调用。同步时，窗口已结束较久（如超过 30 天）的徽章直接跳过；未开始的也跳过。

### 5. 解锁通知

事件触发常发生在管理员审核时，用户不在线，不能再依赖 `sync` 返回的 `newlyUnlocked` 当场弹窗。

- 获得记录增加 `notified: false`。
- 用户打开小程序或成就页时，拉取未通知的记录弹出解锁动画，然后标记为已通知。
- 老记录视为已通知。

### 6. 系列展示方式

成就页按系列自动选择排法，不需要配置：

- 系列里有任一徽章带时间窗口 → `grid`：按 `sort` 平铺，每枚显示「未开始 / 进行中（倒计时）/ 已获得 / 已错过」。
- 否则 → `ladder`：现有阶梯展示，同一统计项按门槛排，显示累计进度。

现有系列都不带时间窗口，展示不受影响。

## 索引

窗口查询需要以下组合索引，上线前在控制台建好：

- `photo`：`_openid + verified + create_date`
- `comment`：`_openid + create_date`
- `inter`：`_openid + type + create_date`

## 开发阶段

每个阶段单独可上线，后一阶段不阻塞前一阶段的使用。

| 阶段 | 内容 | 完成后可用的能力 | 预估 |
|---|---|---|---|
| 1 ✅ | 规则结构 + 注册表 + 窗口 / 聚合 / 筛选计数，发放仍走 `sync`；建索引 | 后端已能发放各类新规则徽章（暂时手工写库配置） | 1～1.5 天 |
| 2 ✅ | 后台编辑器：窗口、聚合、筛选 | 管理员可在后台配置任意新规则徽章 | 1 天 |
| 3 | 前端 `grid` 展示与四种状态 | 时间限定类系列有正确的展示 | 1.5～2 天 |
| 4 | 事件触发 + 解锁通知 + 兜底同步调整 | 审核通过即发放，用户下次打开时弹窗 | 1.5～2 天 |

合计约 5～7 个工作日，另需留出真机联调和灰度验证时间。阶段 1～3 完成后即可上线时间限定类成就；阶段 4 主要改善时效和体验，可紧随其后。

## 使用指南（开发完成后补充）

开发完成后在此补充操作步骤，以「新建一个节气系列」为例：批量新建徽章、设置窗口、上传正面图、上线与验证。

## 待定事项

- 照片窗口依据用上传时间还是拍摄时间（`shooting_date`）。拍摄时间更贴合「节气当天拍的照片」，但可由用户填写，存在补传旧照的问题。本设计默认用上传时间。
- 取消点赞后，已发放的点赞类徽章不收回（与现有累计徽章一致）。
